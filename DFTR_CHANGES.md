# Dftr changes

Every change this fork carries on top of upstream, newest first: what changed, why, the test that
holds it, and whether upstream has it (AGENTS.md §12 in github.com/BashirAbu/RustyDftr).

Base: upstream release tag `v0.8.3`.

| Commit | What changed | Why | Test | Upstream has it |
|---|---|---|---|---|
| `5c82005` | COMPAT.md: the WITH clause row says `WITH RECURSIVE` is supported and lists the limits the planner enforces: those of `prepare_recursive_cte_plan` (`core/translate/planner.rs`), which SQLite has too, and the refusal of a FULL OUTER JOIN with the CTE in a recursive SELECT (`core/translate/optimizer/join.rs`), which SQLite does not have | The row still said `WITH RECURSIVE` was not supported, though it has been since 0.8.0 (CHANGELOG), and Dftr's tree documents rely on it | Documentation only. The limits are the errors `recursive-cte.sqltest` expects (`recursive-cte-first-term-self-reference-rejected`, `-circular-reference-in-subquery`, `-multiple-direct-references`, `-multiple-nested-references`, `-non-recursive-term-after-recursive-rejected`, `-aggregate-rejected`, `-window-rejected`, `-full-join-recursive-on-left-not-supported`); the two `UNION`-operator refusals have no test. What is supported is covered by that file and by the tests of `4a972ee` | no: v0.8.3 has the old line; not checked since |
| `4a972ee` | Integration tests for recursive CTE queries over a table with `id TEXT PRIMARY KEY, parent_id TEXT` and an index on `parent_id`, with bound parameters and one prepared statement reused for several values, each run on a plain and an aegis256-encrypted database: a group and its descendants, alone and as an `IN` filter in a larger query (LEFT JOIN, another condition, ORDER BY, LIMIT, OFFSET; the CTE at the statement's top and inside the `IN`); an entry and its ancestors; whether one entry is an ancestor of another; a parent cycle under `UNION` (each row once) and under a depth-limited `UNION ALL`; each group's count and sum with its descendants. Tests only: they all passed on the unchanged code | Dftr's tree documents filter lists and reports to a group's subtree, walk ancestors, refuse moves that make a cycle and total over descendants with these queries; the fork's coverage (`recursive-cte.sqltest` in memory, and two integration tests) ran none of them with bound parameters, over a TEXT key with a parent index, or on an encrypted database | `recursive_cte_lists_a_group_and_its_descendants`, `recursive_cte_filters_a_larger_query_to_a_group_and_its_descendants`, `recursive_cte_lists_an_entry_and_its_ancestors`, `recursive_cte_finds_whether_an_entry_is_an_ancestor_of_another`, `recursive_cte_union_returns_each_row_of_a_parent_cycle_once`, `recursive_cte_union_all_stops_a_parent_cycle_at_a_depth_limit`, `recursive_cte_counts_and_sums_each_group_with_its_descendants`, each with an `_encrypted` variant (`tests/integration/query_processing/test_read_path.rs`) | no: these tests are Dftr's; upstream has the feature itself since 0.8.0 |
